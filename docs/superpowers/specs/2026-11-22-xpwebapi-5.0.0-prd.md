# xpwebapi 5.0.0 product requirements

Release scope approved on 2026-11-22 in the planning conversation. The
maintainer answered “yes to all” to the proposed 5.0.0 scope and capture
profiles for manual launches. Work-item approvals remain recorded in their
own plans and decisions.

## Release outcome

Deliver a Python 3.12 release with typed X-Plane v3 flight management,
configurable capture setup, and validated FDR coordinate ingestion. The
published baseline is `v4.0.0` at `2518aed3b234bf3aca73323d452f33628258d65f`.
The pending Python 3.13 removal and the HTTPX2 client and exception types
require a major increment. The selected pending target is `5.0.0`.
Package, runtime, and lock versions track that pending target.

## Included requirements

1. Complete the source-layout move in [issue #2](https://github.com/tvproductions/xplane-webapi/issues/2)
   while preserving import names, entry points, and packaged resources.
   Refresh its design and acceptance plan to reconcile the old Python 3.13
   installation requirement with the proposed 3.12-only release. Preserve
   the roadmap's source-layout prerequisite for the next two items.
2. Add typed synchronous and asynchronous flight initialization and updates
   in [issue #3](https://github.com/tvproductions/xplane-webapi/issues/3).
   Validate the [official flight request schema](https://developer.x-plane.com/article/flight-initialization-api/)
   and typed results against the [v3 Web API](https://developer.x-plane.com/article/x-plane-web-api/).
   Require an aircraft and one start location for initialization. Updates
   preserve omitted fields and reject attempts to change the aircraft or
   start location. Both write operations must enforce the existing read-only
   policy before transport. Approve the design after the layout move.
3. Provide human-facing capture setup that uses `pydantic-settings` with a
   documented precedence for explicit options, environment, and selected
   profiles. Preserve the worker's protocol, request provenance, and output
   preflight. The proposed [capture settings decision](ADR-0001-001-resolve-capture-settings-before-worker-launch.md)
   records the boundary and precedence for separate architectural approval.
4. Integrate the existing FDR implementation under [issue #5](https://github.com/tvproductions/xplane-webapi/issues/5).
   Review its approved specification before changing the implementation plan.
   Use Pydantic coordinate validation at ingestion while preserving strict
   numeric input, valid legacy recordings, public FDR errors, and GeoJSON
   longitude-first output. The FDR design must account for any new runtime
   dependency.

The Python 3.12 and HTTPX2 transition is already in the development tree.
This scope leaves NUL handling, the FDR viewer, upstream intake automation,
Backplane activation, and changes to gzkit or gz-starter outside the release.

## Acceptance

- The source-layout, flight, capture, and FDR contracts pass standard-library
  unittest coverage, including input validation, precedence, read-only
  enforcement, and behavioral compatibility.
- The existing hygiene, strict documentation, wheel, source archive, and
  installed-command checks pass on the approved Python patch. Release
  metadata verifies the selected Python support range.
- Recorded simulator checks exercise the supported API v3 operations and the
  FDR output assumptions. Publication requires separate authorization and
  the existing release gates.
